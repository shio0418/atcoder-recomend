# AtCoder精進コーチ Design Doc

## 概要

AtCoderの提出履歴を蓄積し、自分の弱点・詰まりパターンを可視化＋復習に導く「パーソナル精進コーチ」。

一般的な問題管理は「AC→解けた／WA→解けなかった」で終わるが、本サービスは以下の学習サイクルそのものを管理する。

```
問題 → 初回提出 → WA → コード分析 → 原因分類 → 数日後に復習推薦 → 再挑戦 → AC
```

## 目的・背景

- 「自分のために作る」を軸に選定した個人開発テーマ
- ML/MLOps/バックエンド系インターン応募用のポートフォリオ作品を兼ねる
- 既存の類似サービス（AtCoder Problems、AtCoder Tagsなど）は分野の静的可視化止まりであり、①復習の仕組み化、②詰まり理由の蓄積・パターン化、という点で差別化する
- 各Phaseを明確なゴールというより土台として設計し、Phase0/Phase1で早期に「使える」状態を作ることを重視する

## コア価値提案

単発のLLM診断で終わる既存ツールと違い、復習の仕組み化と詰まり理由の蓄積・パターン化まで踏み込む。

## 開発フェーズ

### Phase 0（基盤）
- AtCoder提出履歴取得
- LLMで分野分類（事前バッチ処理、推薦のたびには呼ばない）
- 分野別正答率の可視化 → Phase1のレコメンドロジックに統合する方針（単体機能としては作らない）

### Phase 1（コア機能）
次に解くべき問題のレコメンド。

- ルールベース（弱点タグ×難易度バンド×忘却曲線）から着手
- レコメンド結果表示画面を最初のフロントエンドの主軸にする

### Phase 2（差別化ポイント／MLOps要素の導入）
提出コード＋ACコードをLLMで診断（「どこで詰まったか」）し、蓄積して繰り返しパターンを検出する。

- 実装難易度・精度の不確実性が高いため、着手前に少数サンプルでの手動PoC（プロンプトの効果検証）を先に行う
- 診断精度のモニタリング：分類・診断結果の一部を定期的に人力サンプリングして精度をチェックする仕組みを軽く入れる（本格的な自動評価はPhase3で）
- 推論コスト・レイテンシの記録：LLM呼び出し回数・トークン数・応答時間をログとして残す（後のコスト最適化の材料にする）。診断機能(#19)自体の成否に関係なく、既に動いているJev分類呼び出しに対して先に導入できる
- embeddingベースの類似問題検索：タグ検索だけでは同じタグでも実装難易度・発想の難しさが異なる問題を区別できないという限界があるため、問題文をembedding化してpgvectorで類似検索できるようにする。タグ検索（粗いフィルタ）とembedding類似度（詰まった問題に近い問題の絞り込み）を組み合わせる設計。「詰まった問題の類題を復習で提示する」というユースケースに対応し、Phase1の忘却曲線（いつ復習するか）と組み合わさることで「何を復習するか」まで踏み込める

### Phase 3（コアMLOps要素）
- AtCoder Problems API経由で他ユーザーの提出データを取得し、協調フィルタリング（「似た解答傾向のユーザーが次に解いた問題」）による推薦モデルを構築
- 実験管理：MLflowまたは類似ツールでモデルのパラメータ・精度指標を記録
- 評価パイプラインの自動化：precision@k等のオフライン評価をスクリプト化し、モデル変更のたびに再実行できるようにする
- モデルバージョニング：どのバージョンのCFモデルが本番相当で使われているかを追跡
- 推論サービス分離：gRPCでPython推論サービスを切り出し、バックエンド(Go)から呼び出す構成にする。サービス分離自体がMLOps的な設計判断（推論と業務ロジックの責務分離）
- モニタリングの発展：Phase2で始めたログ収集を土台に、推論のレイテンシ・コスト・精度推移をダッシュボードで見える化する
- 観測性（ログ・メトリクス）：Phase2で導入予定の推論コスト・レイテンシ記録を、DB接続失敗やAPI呼び出し失敗の頻度など、アプリ全体に広げる
- 負荷対策（仮に複数ユーザーが使う場合を想定）：AtCoder APIレスポンスのキャッシュ、DBコネクションプーリング（`cmd/api`は`pgxpool.Pool`へ切り替え済み、他の`cmd/*`バッチ系は単一`Connection`のまま使い分け）、分類バッチの非同期ジョブ化。自分専用サービスの現状では優先度は低いが、設計判断として言語化しておく
- 負荷試験（優先度低、Phase1完了後）：実際は自分専用サービスで同時アクセスは想定しにくいため急ぎではないが、非機能要件（特にDBコネクションプーリング）の効果を実測で裏付ける材料として実施する。vegetaまたはk6でレコメンドAPI等に対してリクエストレートを変えながら負荷をかけ、レイテンシ分布・エラー率を計測する。`pgxpool`導入前後の比較（例：p99レイテンシの変化）を記録し、非機能要件の説明に実測値を添える

課題：データ量の確保、コールドスタート、評価ラベル設計。

### MLOps要素の位置づけ
Phase0〜1はほぼ純粋なバックエンド開発。MLOps色を出すのはPhase2の「モニタリングの下地作り」から、Phase3の協調フィルタリング実装が本命。

## 技術スタック

| 領域 | 技術 |
|---|---|
| バックエンド | Go |
| LLM推論サービス | Python + gRPC（Phase3〜） |
| フロントエンド | React / Vite（recharts等） |
| DB | PostgreSQL |
| インフラ | VPS + Docker Compose（自前デプロイ） |

### PostgreSQLを選んだ理由
- データが構造化されており、テーブル間のJOIN・集計を前提としたモデル
- pgvectorにより、Phase2/3で必要になりうるベクトル検索を同一DB内で完結できる
- Goとの実装実績あり（pgx）

## DBスキーマ

マイグレーションファイル（`backend/migration/*.sql`、gooseで管理）が唯一の正しい情報源。スナップショットのschema.sqlは意図的に廃止した（マイグレーションとの内容の食い違いが実際に起きたため）。

## 技術選定・設計判断の理由（面接想定メモ）

判断のたびに追記していく。

| 判断 | 理由（要約） |
|---|---|
| PostgreSQL vs MySQL | pgvectorでembedding検索まで一元化できる、Goとの実装実績（pgx） |
| `problems.id`はSERIAL、UUIDにしない | 単一DB・単一サービスで分散ID発行の必要が無い、IDを外部公開しない |
| `submissions.submission_id`はBIGINT | 外部システム（AtCoder）が発行するIDのため、値域を自分側で保証できない |
| `submissions.problem_id`にUNIQUE制約をつけない | 同一問題への複数回提出（WA→WA→AC）を追跡することが核 |
| `category_stats`のような集計専用テーブルを持たない | 現状の規模ならJOIN＋GROUP BYで都度集計しても問題ない。必要になれば materialized view |
| `submissions.problem_id`に外部キーとは別にINDEXを追加 | `REFERENCES`は参照整合性のみ保証、検索用インデックスは別途必要 |
| レコメンド機能（Phase1）をLLM診断（Phase2）より優先 | 自分が最も欲しい機能。診断機能はデータが蓄積するまで価値を実感できない |
| LLMによる分野分類は事前バッチ処理、推薦のたびには呼ばない | レイテンシ・コストの無駄を避ける |
| 分類のタグは事前定義したリストから選ばせる | 自由生成だと表記揺れ（「DP」「動的計画法」など）が起きる |
| 分類の出力は`problem_id`で紐付け（`index`不使用） | 順番のズレによる誤対応リスクを避ける |
| マイグレーション管理にgooseを導入 | 手動`ALTER TABLE`を2回忘れて詰まった実体験から、適用漏れを構造的に防ぐため |
| タグ分類のバックエンドをGemini→Jevへ移行 | コスト（想定の3〜4倍に膨らんだ）とレート制限（無料枠20req/日、spend cap）の問題。Jevはコスト1/30程度（実測: 全9532件で1ドル程度）で同等〜以上の精度を達成。実際に全件（9310/9532、約97.7%）タグ付け完了済み |
| 提出コード診断機能（Phase2本体）をPoC後に見送り、embedding類似検索・協調フィルタリングを優先 | PoC（#20）自体は精度良好（WA+ACコードからオーバーフロー原因を的確に診断）だったが、実装してもJevのタグ分類と構造的に同じ（LLM単発呼び出し）でMLOps的な学びが薄い。協調フィルタリング（Phase3）は学習・評価・モデルバージョニング・Python+gRPCでの推論サービス分離が必然的に要るため、MLOps要素として質・量ともに上位互換。PoCで実現可能性は検証済みなので、いつでも再着手できる状態にしてある |
| embeddingモデルはe5（`intfloat/multilingual-e5-small`）を採用、StaticEmbeddingは不採用 | 用途が9316件の一括バッチ処理（一度きりの実行）であり、リアルタイム推論の速度は要件にならない。精度を優先する方が合理的と判断。後日、自由テキスト検索機能（1件だけのクエリembedding）を実装した際も実測で十分高速だったため、e5のままで要件を満たせることを確認済み（StaticEmbeddingへの切り替えは不要だった） |
| 自由テキスト検索もembeddingサービスを使い回し、新しいモデル/サービスを作らなかった | 検索1件のembedding生成はバッチの9316件と違って単発呼び出しで済み、既存の`EmbedBatch`（1件のmapを渡すだけ）をそのまま再利用できた。モデルの冗長な多重管理を避けられる |
| embedding生成を外部API直叩きではなく自前ホスト（Python + gRPC）にした | 外部embedding APIをGoから直接叩くだけならJevと同じ構造（単発HTTP呼び出し）になり、gRPC/Pythonインフラの実践にならない。Phase3の協調フィルタリングで必然的に必要になるPython推論サービス分離のパターンを、データが単純でリスクの低いembeddingタスクで先に通しておく狙い |
| embeddingサービスのgRPC通信を双方向streamingにした（unary batchにしなかった） | 9316件を一度に送受信すると、送信専用ループの間に受信側が詰まりgRPCの内部バッファが溢れてデッドロックしうる。送信と受信を別goroutineで並行させ、結果が出た分からDB書き込みできるようにすることで、メモリ使用量を抑えつつパイプライン化した |
| `problems.embedding_model`列でモデルバージョンを記録 | embeddingモデルを将来変更した際、どの行が古いモデルで生成されたか機械的に判定できるようにするため。`WHERE embedding_model != '新モデル名'`で再生成対象を差分抽出できる |
| 推論コスト・レイテンシの記録を`inference_calls`という汎用テーブルに統一 | Jevの分類呼び出しとembedding呼び出しは「外部/自前の推論を呼んでレイテンシ・成功失敗を記録したい」という点で同じ構造。呼び出し元ごとに個別のログテーブルを作らず、`call_type`で区別する1つのテーブルにまとめた |
| 類似問題検索をembedding類似度とタグの重なりで2本立てにし、1つのスコアに混ぜない | 複合confidenceスコアを作らない方針（Phase0から一貫）の延長。`/api/similar`（embedding）と`/api/similarByTag`（タグ配列の`&&`演算子）を独立したエンドポイントにして、フロントにも両方表示。精度の違いを比較できる副次的な利点もある |
| 忘却曲線にWA回数を組み込んだ（`interval = baseInterval / (1 + waCount)`） | 実データではほぼ全問題の`acCount`が1のままで、既存の式`5 * 2^(acCount-1)`が常に5日固定になり事実上機能していなかった。`submissions`に既にある非ACの提出回数（`result != 'AC'`）は1回目の復習時点から差が出る値なので、`acCount`が育つまで効果が出ないという弱点を補える。difficultyベースの補正（issue #532の`f(p,i)`項）はより検証コストが高いため保留 |
| CFのデータ収集は`standings/json`ではなく終了済みコンテストの`results/json`を使用 | `standings/json`は未ログイン状態だとサインインページにリダイレクトされ取得できない（ライブ中の順位表を覗き見されないための制限と推測）。`results/json`（終了済みコンテストの最終結果）は未ログインでも取得できたため、こちらを採用。他ユーザーの公開データを、意図された制限を回避せず取得する方針とも合致 |
| 協調フィルタリングはメモリベース（近傍ベース）を採用、モデルベース（ALS等の行列分解）は見送り | ユーザー×問題の疎行列に対してコサイン類似度を計算するだけで、学習の最適化ループを持たない。k近傍法(k-NN)と同じ「lazy learning」に分類される正式な機械学習手法であり、モデルベースCFと並ぶ協調フィルタリングの一分野。まず軽量な手法で実装・評価し、必要になればモデルベースを発展版として検討する方針 |
| CFの人気バイアス補正（tf-idf的な重み付け）を、ベースライン比較用の「人気推薦」には適用しない | 補正は「類似ユーザーの探索」というCF固有の工夫であり、比較対象（素朴な人気推薦）にも適用すると、何と比較しているか分からなくなる。ベースラインはあえて最も素朴な戦略のまま保つ |
| CFにハイブリッド補正（弱点タグ優先の再順位付け）を追加するにあたり、先行事例（[sucrose氏のAOJでの実装](https://sucrose.hatenablog.com/entry/2014/04/26/000334)）を明示的に参照 | 同種の課題（競プロ判定サイトでの協調フィルタリング問題推薦）に対する2014年の先行事例と酷似するリスクを認識し、隠さず参照元として明記。差別化は（1）Phase0のタグ・Phase2のembeddingという本プロジェクト独自のコンテンツシグナルとの組み合わせ、（2）precision@k・ベースライン比較による定量評価、の2点で担保 |
| CFハイブリッド版のprecision@10低下（0.422→0.396）を許容して採用 | precision@kは「ユーザーが実際に解くか」を当てる指標であり、ユーザーの得意分野に寄せた推薦ほど高く出やすい。弱点克服を優先するハイブリッド補正は、プロダクトの本来の目的に沿うための意図的なトレードオフであり、指標の低下は設計の欠陥ではなく指標自体の限界を示す結果と判断 |
| CFサービスのgRPC通信はunary RPC（embeddingの双方向streamingとは異なる） | CFの推薦は「ユーザー1人分をリクエストして1回レスポンスを受け取る」という単発のやり取りで完結し、embeddingのような大量データの双方向フローが発生しない。streamingは不要と判断 |
| CFの実験管理（MLflow）はローカルファイルベースで運用、リモートサーバーは構築しない | 個人開発・単独利用の規模でチーム共有は不要。将来VPS上で定期学習するようになっても、ローカルファイルのまま運用でき、必要になった時点で移行すればよい |

## 競合・類似サービス調査

| サービス | 何をやっているか | このプロダクトとの関係 |
|---|---|---|
| AtCoder Problems / AtCoder Tags | 分野の静的可視化 | Phase0の可視化は縮小し、レコメンド結果表示に統合 |
| kikutak1182/problem_recommend | ルールベース＋embedding類似度＋LLM妥当性スコアの3シグナル統合タグ付け（108タグ定義）、タグ×レートでのレコメンド | タグ*名称*のみ語彙として参考にした。分類*結果*（`problems_data.json`）はカバレッジ12%・精度検証不能・ライセンス無しのため不採用 |
| AtCoder-Ebbing（2021） | 忘却曲線ベースの復習問題出題 | サービス自体は現在リンク切れ。着眼点に先行事例はあるが稼働中のものは無い |
| kenkoooo/AtCoderProblems Issue #532 | 忘却曲線復習機能の設計議論（2020〜2022）。間隔計算式 `d_i := 5 * 2^(i-1) - f(p, i)` を提案するも「WAだったかの自動判定が困難」という壁に2年以上ぶつかり頓挫 | **本プロダクトの`submissions`テーブルは全提出（WA含む）を時系列で保存する設計にしており、この壁を設計時点で解消している**。間隔計算式自体は参考にして実装する方針 |

## 非機能要件・今後の改善（優先度順）

1. 外部API障害への耐性 → リトライ・指数バックオフは実装済み（AtCoderスクレイピング・Gemini/Jev呼び出し双方）
2. バッチ処理の再開可能性 → `statement IS NULL`/`tags IS NULL`による差分実行で実質対応済み
3. 単体テストの整備 → 主要な純粋関数（recommend, classifier, client）に実装済み。DB依存のrepository層は未対応
4. CI（GitHub Actions）→ 実装済み（push/PR時にbackend/frontend双方をbuild・test）。CDは本番インフラ未構築のため未着手
5. 観測性（ログ・メトリクス）
6. 負荷対策（複数ユーザー想定時）：現状優先度低いが判断は言語化しておく。`cmd/api`は`pgxpool.Pool`で並行リクエストに対応済み、CORSも既知のフロントオリジンのみ許可

## LLM APIコスト削減方針

1. ルールベースで済む処理はLLMを呼ばない → 判断: 実装コストの割に効果が薄く、Phase0では見送り
2. 軽量モデルをデフォルトにする → Jev移行でほぼ解決
3. Batch APIを使う → Jev移行により優先度低下（Jevが十分安いため）
4. プロンプトキャッシュを使う → 同上
5. 出力トークンを制限する → Jevは出力トークンが無料のため実質解消
6. 推論コスト・レイテンシの記録 → 未実装、Phase2で導入予定
